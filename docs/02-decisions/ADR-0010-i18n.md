# ADR-0010. Multilingual support

## Context

The system is localized in three languages: Russian, English, Turkish. The
dictionaries contain ~1,700 messages per language; the frontend uses `react-intl`
2.4 with a 1,573-line message declaration file and a separate extraction script
via Babel. The backend has an `i18n` directory in its resources and
`messages*.properties` files in the separate services — that is, **the messages
live in two places in two different formats**.

The message keys in the current system are opaque and partly coincide with
transliterated field names from the inherited ERP.

## Decision (proposed)

1. **The three languages are preserved** — ru, en, tr. Dropping a language is a
   product decision
   ([C-07](../00-context/03-constraints.md#c-07-multilingual-support-is-mandatory)).
2. **One message source for the whole system.** Server-side messages (validation
   errors, texts in reports, emails, SMS) and client-side ones come from one
   store in one format. There is no duplication of dictionaries.
3. **Keys are meaningful and hierarchical**, tied to the domain and the screen
   rather than to a field name from the inherited system.
4. **Everything the user sees is localized**, including the texts of errors
   arriving from the backend: the server returns an error code and parameters,
   not a ready-made phrase ([ADR-0005](ADR-0005-contract-first-api.md)).
5. **Numbers, dates and currencies are formatted according to the user's
   locale**, by a single mechanism rather than by hand on each screen.
6. **A missing translation is detected in CI**, not by a user: checking
   dictionary completeness is part of the build.
7. **Language is a property of the user**, stored on the server rather than in a
   cookie next to the token as it is today.

## What is deliberately not carried over

- Extracting messages through the Babel build and writing them into a file.
- Transliterated keys.
- Separate `messages.properties` in every service.

## Consequences

- Carrying over ~1,700 messages ×3 languages together with a rework of the keys
  is measurable work; it must be estimated rather than assumed "free". →
  [EPIC-008](../../backlog/EPIC-008-i18n-migration.md)
- It must be decided who maintains the translations after launch and how: a
  developer in the code, or a content owner through a translation tool. The
  choice of message store depends on that. →
  [OQ-010](../../transition/12-open-questions.md)
- Reports and printable forms are localized too — that is a requirement on the
  reporting subsystem ([ADR-0009](ADR-0009-reporting-and-exports.md)).
- The test data and the reference values for the cutover reconciliation must take
  the locale into account, otherwise comparing reports will produce false
  divergences.
