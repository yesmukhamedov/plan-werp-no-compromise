# Внешние интеграции и потребители API

Всё, что подключено к WERP снаружи. Каждая позиция — обязательство, которое
новая система принимает на себя без изменения контракта ([C-05](03-constraints.md#c-05-внешние-интеграции-менять-нельзя)).

Инвентаризация контрактов — обязательная работа Фазы 0
([EPIC-002](../../backlog/EPIC-002-contract-inventory.md)); эта таблица —
её отправная точка, а не результат.

## Схема связей

```
                 внешний мир
                      │
                 ┌────┴─────┐
                 │  bridge  │   Go, allowlist маршрутов, не переписывается
                 └────┬─────┘
        ┌─────────────┼─────────────┬──────────────┐
        ▼             ▼             ▼              ▼
     auth          core         service          crm
        │             │             │              │
        └─────────────┴──────┬──────┴──────────────┘
                             ▼
                      база данных
```

Веб-фронтенд обращается к внутренним сервисам **напрямую**, минуя `bridge`
(отсюда захардкоженные адреса контуров в бандле — [P-08](02-pain-points.md#p-08-конфигурация-окружений-зашита-в-код)).
Целевая схема это меняет — см. [03-target/01-architecture.md](../03-target/01-architecture.md).

## Исходящие и входящие интеграции (через `bridge`)

| Интеграция | Направление | Что делает | Кто владеет контрактом |
|---|---|---|---|
| Платёжный провайдер | входящее | приём платежей, сверка | контрагент |
| Кредитное бюро | исходящее | кредитный рейтинг по идентификатору клиента | контрагент |
| SMS-провайдер | исходящее + вебхук | рассылка и отчёты о доставке | контрагент |
| Мессенджер (WhatsApp) | двустороннее | отправка, приём, список сообщений | контрагент |
| Формы публичных сайтов | входящее | заявки с лендингов → CRM | наш, но публичный |
| Мессенджер-суперапп | входящее | заявки, электронная подпись | контрагент |
| Мессенджер для операторов | двустороннее | интегрирован напрямую в колл-центр, минуя `bridge` | контрагент |

## Потребители внутреннего API

| Потребитель | Через что | Жёсткость контракта | Переписывается? |
|---|---|---|---|
| Веб-фронтенд | напрямую | контракт определяем мы | **да**, вместе с бэкендом |
| Мобильное приложение | `bridge`, фиксированный allowlist путей | **1:1, изменения запрещены** | нет ([C-06](03-constraints.md#c-06-мобильное-приложение--отдельный-клиент-вне-этого-плана)) |
| Легаси-JSF | общие cookie, общая БД | будет выведен из эксплуатации | нет, удаляется |
| Внешние интеграции | `bridge` | 1:1 | нет |
| Внутренние сервисы друг к другу | Feign / HTTP | контракт определяем мы | да |

## Что это значит для плана

1. **`bridge` — граница ответственности.** Всё, что за ним, мы переписываем
   свободно. Всё, что перед ним, — обязательства перед третьими лицами.
   Единственное требование к новой системе: предоставить `bridge` тот же набор
   внутренних эндпойнтов.

2. **Мобильный контракт — самое жёсткое ограничение проекта.** Список путей,
   открытых для мобильного приложения, зафиксирован в `bridge`
   (`internal/routes/mobile.go`) — это готовая, проверенная спецификация
   обязательного минимума. Она становится входными данными для
   [EPIC-002](../../backlog/EPIC-002-contract-inventory.md).

3. **Внутренние вызовы между сервисами сейчас идут через Feign** — при big bang
   этот слой исчезает вместе со старой топологией, и заменять его один в один не
   требуется.

4. **Мессенджер для операторов подключён к колл-центру напрямую**, минуя
   `bridge`, — это исключение из общей схемы. При переписывании его нужно либо
   провести через `bridge` (предпочтительно, единообразие), либо явно
   зафиксировать исключение в ADR.
