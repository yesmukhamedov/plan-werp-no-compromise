# Модель данных

Правила, по которым устроено хранилище нового WERP. Конкретный механизм доступа
к данным зависит от стека `[STACK]` ([ADR-0003](../02-decisions/ADR-0003-backend-stack.md));
всё остальное здесь — от стека не зависит.

## Организация

- Одна база PostgreSQL ([ADR-0002](../02-decisions/ADR-0002-database-postgresql.md)).
- **Схема на домен**, имя схемы = имя домена из [карты](02-domain-map.md).
- Домен пишет и читает только свою схему ([NC-02](../01-principles/01-no-compromise.md#nc-02)).
- Внешние ключи — только внутри схемы. Между доменами — ссылка по идентификатору
  без ограничения целостности на уровне БД; целостность обеспечивает
  прикладной слой.
- Общие для всех справочники (валюты, страны, единицы измерения) живут в схеме
  домена «Справочники» и доступны другим доменам **через его публичный
  интерфейс**, а не прямым запросом.

## Именование

| Объект | Правило | Пример |
|---|---|---|
| Схема | `snake_case`, имя домена | `accounting` |
| Таблица | `snake_case`, единственное число | `contract`, `posting` |
| Столбец | `snake_case` | `created_at`, `total_amount` |
| Первичный ключ | `id` | |
| Внешний ключ | `<сущность>_id` | `customer_id` |
| Индекс | `ix_<таблица>_<столбцы>` | `ix_contract_customer_id` |
| Уникальный индекс | `ux_<таблица>_<столбцы>` | |
| Ограничение | `ck_<таблица>_<смысл>` | |

**Транслитерация и унаследованные сокращения запрещены.** Текущие имена вида
`bukrs`, `matnr`, `lifnr`, `werks` расшифровываются один раз в
[GLOSSARY.md](../../GLOSSARY.md) и заменяются осмысленными. Это отдельная,
обязательная работа при миграции — таблица соответствия старых и новых имён
становится частью инструмента переноса данных.

## Обязательные столбцы

Каждая изменяемая сущность имеет:

| Столбец | Назначение |
|---|---|
| `id` | первичный ключ |
| `created_at`, `created_by` | кто и когда создал |
| `updated_at`, `updated_by` | кто и когда изменил последним |
| `version` | оптимистическая блокировка |

Удаление — логическое (`deleted_at`, `deleted_by`) везде, где запись может
участвовать в истории или отчётности; физическое — только там, где это
безопасно и обосновано.

## Типы

| Что | Тип | Почему |
|---|---|---|
| Деньги | `numeric(19,4)` + отдельный столбец валюты | точность обязательна ([C-09](../00-context/03-constraints.md#c-09-финансовые-расчёты-требуют-точной-арифметики)) |
| Проценты, коэффициенты | `numeric` с явной точностью | то же |
| Момент времени | `timestamptz`, хранение в UTC | часовой пояс не зашивается |
| Дата | `date` | |
| Идентификатор | решение платформы, единое для системы | |
| Перечисление | текстовый столбец с ограничением-проверкой | значения читаемы в БД и в выгрузках |
| Флаг | `boolean` | не `char(1)` и не `number(1)`, как в унаследованной схеме |
| Полуструктурированные данные | `jsonb`, только с обоснованием | не как способ избежать проектирования схемы |

**Числа с плавающей точкой для денег и количеств запрещены** — проверяется
автоматически по схеме.

## Правила денежной арифметики

Определяются **один раз** на уровне платформы и не переопределяются в доменах:

- точность хранения — 4 знака после запятой; точность представления — по валюте;
- правило округления — задаётся явно, единое для системы, документируется здесь
  после подтверждения бухгалтерией;
- сумма всегда сопровождается валютой; сложение сумм в разных валютах —
  ошибка времени выполнения, а не молчаливое приведение;
- курсы валют — версионированный справочник с датой действия; расчёт всегда
  указывает, на какую дату взят курс.

Расхождение с расчётами текущей системы при сверке — **ноль**, без допуска
([04-migration/03-parity-verification.md](../04-migration/03-parity-verification.md)).

## Миграции

- Только версионированные, только вперёд, только через инструмент миграций.
- Каждая миграция применяется на копии промышленных данных до слияния.
- Ломающие изменения — в четыре шага: добавить → заполнить → переключить →
  удалить, каждый в отдельном релизе.
- Автогенерация схемы в рантайме отключена во всех контурах, включая
  разработческий: иначе схема в разработке и в проде расходятся незаметно.
- Эталонные (справочные) данные версионируются вместе со схемой.

## Аудит

Требование [C-10](../00-context/03-constraints.md#c-10-аудит-изменений-уже-существует-и-должен-сохраниться).

- Аудит — подсистема платформы, единая для всех доменов, а не механизм ORM,
  подключаемый по вкусу домена.
- Что аудируется — решение владельца домена, зафиксированное явно; аудит «всего»
  и аудит «ничего» одинаково бесполезны.
- Запись аудита неизменяема, содержит: субъекта, время, сущность, действие,
  прежнее и новое значения, идентификатор запроса.
- История из текущей системы (таблицы Envers) мигрирует вместе с данными.
- Срок хранения записей аудита — [OQ-003](../08-risks/02-open-questions.md).

## Производительность

- Индекс создаётся под конкретный запрос, а не «на всякий случай»; каждый индекс
  имеет обоснование в описании миграции.
- Запросы профилируются на объёме, сопоставимом с промышленным.
- Проблема N+1 отлавливается тестом ([06-quality/01-test-strategy.md](../06-quality/01-test-strategy.md)),
  а не на проде.
- Тяжёлое чтение — с реплики.
- Секционирование крупных исторических таблиц рассматривается по факту
  измеренного объёма, а не заранее.

## Что переносится из легаси и что нет

| Переносится | Не переносится |
|---|---|
| Данные всех действующих сущностей | Таблицы, не читаемые ни одним запросом (выявляются в [EPIC-003](../../backlog/EPIC-003-schema-inventory.md)) |
| История аудита | Столбцы, не заполнявшиеся годами (в текущей системе такие есть — отмечены самими разработчиками) |
| Справочники | Дублирующиеся справочники — сводятся в один |
| Учётные записи (без паролей в открытом виде) | Технические столбцы старой ORM |
| Файлы и вложения | Временные и служебные таблицы |

Решение по каждой таблице принимается в [EPIC-003](../../backlog/EPIC-003-schema-inventory.md)
и фиксируется письменно. «Перенесём на всякий случай» — не решение: так
переносится и мусор, и вместе с ним старая модель.
