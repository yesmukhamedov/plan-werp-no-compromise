# Стратегия тестирования

Текущая система имеет **4 тестовых файла на 354 761 строку** и собирается в CI
с `-x test` ([P-01](../docs/00-context/02-pain-points.md#p-01-тестов-практически-нет)).
Это первопричина большинства остальных проблем: без тестов нельзя рефакторить,
поэтому новое пишут рядом, поэтому появляются дубли доменов.

[NC-01](../docs/01-principles/01-no-compromise.md#nc-01) отменяет это правилом.
Здесь — как оно исполняется.

## Уровни

| Уровень | Что проверяет | Где выполняется | Доля |
|---|---|---|---|
| Модульные | доменные правила, расчёты, инварианты | без БД и HTTP | основная масса |
| Интеграционные | домен + настоящая PostgreSQL в контейнере | контейнер | много |
| Контрактные | соответствие реализации спецификации API | контейнер | по эндпойнту |
| Архитектурные | границы доменов, правила зависимостей | статически | несколько, но обязательны |
| Сквозные | сценарии из реестра через всю систему | предпродуктивный контур | по сценарию |
| Характеризационные | фиксация поведения **старой** системы | отдельно | Фаза 0 |
| Нагрузочные | НФТ | предпродуктивный контур | регулярно |
| Миграционные | корректность переноса данных | на копии данных | каждая репетиция |

## Что проверяется автоматически

Правила [NC-01…NC-15](../docs/01-principles/01-no-compromise.md) исполняются машиной,
а не ревьюером. Каждой строке соответствует проверка в CI:

| Правило | Проверка | Результат нарушения |
|---|---|---|
| NC-01 | порог покрытия ветвлений; grep на отключение тестов в конфигурации сборки | PR не сливается |
| NC-02 | тест архитектурных правил `[STACK]` | PR не сливается |
| NC-03 | статический анализ: ноль полевых инъекций | PR не сливается |
| NC-04 | линтер: длина класса, метода, число зависимостей | PR не сливается |
| NC-05 | grep на запрещённые механизмы доступа к данным и конкатенацию SQL | PR не сливается |
| NC-08 | сборка в чистом контейнере без кэша | сборка падает |
| NC-09 | сканер уязвимостей зависимостей | критические блокируют |
| NC-10 | grep на `System.out`, `printStackTrace`, `console.log`; проверка `show-sql` в профилях | PR не сливается |
| NC-11 | grep на IP-адреса и имена хостов в исходниках и в собранном бандле | PR не сливается |
| NC-12 | тест: каждый эндпойнт объявляет право | PR не сливается |
| NC-14 | реестр разрешённых библиотек | PR не сливается |
| NC-15 | проверка на запрещённые расширения и размер файлов | PR не сливается |

**Это и есть механизм, отличающий «без компромиссов» от намерения.** Правило,
не проверяемое машиной, соблюдается ровно до первого аврала.

## Характеризационные тесты

Особый тип, существующий только в этом проекте. Пишутся в Фазе 0
([EPIC-004](../backlog/EPIC-004-characterization-tests.md)) **против старой
системы**.

Они не проверяют правильность — они фиксируют факт: «на этих входных данных
старая система даёт такой результат». Включая случаи, где результат
неправильный.

Назначение:

- эталон для сверки паритета ([transition/06-parity-verification.md](../transition/06-parity-verification.md));
- защита от «а мы думали, оно так и работает»;
- единственный способ проверить расчёты, которые нельзя проверить теневым
  прогоном (операции записи, многошаговые процессы).

Приоритет: расчёт вознаграждений (7 598 строк в одном классе), учётные операции,
расчёты по договорам, складские остатки.

## Реестр сценариев

Формируется в Фазе 0 ([EPIC-011](../backlog/EPIC-011-scenario-registry.md)) и
служит одновременно:

- определением полноты новой системы;
- планом сквозных тестов;
- планом ручной приёмки;
- основой сценарного паритета ([transition/06-parity-verification.md](../transition/06-parity-verification.md#уровень-3-сценарный-паритет)).

Формат сценария: кто, что делает, из какого состояния, с каким результатом, как
проверить. Один сценарий — одна проверяемая бизнес-ценность.

## Тестовые данные

- Один способ подготовки данных на систему.
- Данные для теста создаются тестом, а не берутся из общей заполненной базы:
  общая база делает тесты зависимыми друг от друга и хрупкими.
- Копии промышленных данных для предпродуктивного контура **обезличиваются**
  ([product/08-security.md](08-security.md#данные)).
- Эталонные наборы для финансовых расчётов версионируются вместе с кодом.

## Проблема N+1

Отлавливается тестом: интеграционный тест считает число запросов к БД и падает
при превышении ожидаемого. В системе с 523 сущностями и ленивой загрузкой это
единственный способ не обнаружить проблему на проде
([01-principles/03-engineering-standards.md](../docs/01-principles/03-engineering-standards.md#производительность)).

## Скорость прогона

Отслеживаемая метрика. Медленные тесты перестают запускать, а незапускаемые
тесты равны отсутствующим.

| Набор | Бюджет времени |
|---|---|
| Модульные | секунды |
| Интеграционные | минуты |
| Полный прогон на PR | ≤ 15 мин |
| Сквозные | вне PR, по расписанию и перед релизом |

Превышение бюджета — задача, а не данность.

## Покрытие

- Порог покрытия ветвлений доменного слоя: 80 %, проверяется в CI.
- Покрытие — необходимое, но не достаточное условие. 100 % покрытия при
  бессмысленных проверках хуже 70 % при осмысленных.
- Снижение покрытия между PR — повод для отказа в слиянии.
- Покрытие не измеряется по сгенерированному коду.
