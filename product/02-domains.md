# Карта доменов

**Единственный источник истины о том, из чего состоит система.** Модуль кода,
схема в БД, раздел спецификации API, владелец и раздел интерфейса определяются
этой картой и ничем другим. Новый модуль появляется только через ADR
([NC-06](../docs/01-principles/01-no-compromise.md#nc-06)).

Карта — предложение. Она **обязана быть
проверена и уточнена вместе с бизнес-владельцами** до гейта G1: границы доменов
— продуктовое знание, а не результат чтения пакетов.

## Как получена

Текущие 14 предметных областей `core` плюс отдельные модули и репозитории
сведены с учётом дублирования ([P-04](../docs/00-context/02-pain-points.md#p-04-домены-реализованы-дважды)):

| Текущее размещение | Целевой домен |
|---|---|
| `core/general`, `auth-server`, `core/dit` (ABAC), `main-module` (права) | Платформа + Доступ |
| `core/reference` + `core/mreference` | Справочники |
| `core/hr` | Персонал |
| `core/marketing` | Договоры и продажи |
| `core/accounting` (+ `service/maccounting`) | Учёт и финансы |
| `core/accounting` (расчёт зарплаты) | Расчёт вознаграждений |
| `core/logistics` | Склад и логистика |
| `core/service` + модуль `service` | Сервисное обслуживание |
| CRM, колл-центр (четыре источника) | CRM и колл-центр |
| `core/documents` | Документооборот |
| `core/law_department` | Юридический |
| `core/dit` (задачи, сообщения, SMS) | Внутренние задачи и коммуникации |
| `core/aes` | требует уточнения — [OQ-004](../transition/12-open-questions.md) |
| `core/newdev` | требует уточнения — [OQ-004](../transition/12-open-questions.md) |
| `scheduler` | не домен — платформенная подсистема фоновых задач |
| `util` | не домен — растворяется в платформе |

Четыре домена схлопываются из восьми текущих реализаций. Это и есть главный
структурный выигрыш переписывания.

```
       │      │                          ▲
       ▼      ▼                          │
   D6 Вознаграждения          D7 Склад ──┘
```

**Из графа следует порядок разработки в [Фазе 2](../transition/plan/03-phase-2-domains.md).**
При big bang порядок определяется зависимостями, а не бизнес-приоритетом:
промежуточных релизов нет, поэтому «сначала самое ценное» смысла не имеет.

## Правила границ

Формулируются здесь, исполняются тестом архитектурных правил `[STACK]`:

1. Домен обращается к другому домену **только** через его публичный интерфейс
   или через событие.
2. Домен читает **только** свою схему в БД.
3. Ссылки на сущности другого домена — по идентификатору, без внешних ключей
   через границу.
4. Циклических зависимостей между доменами нет. Появление цикла — сигнал, что
   граница проведена неверно; исправляется переносом ответственности или
   заменой синхронного вызова на событие, а не ослаблением правила.
5. Домен не зависит от домена «ниже» себя по графу.
6. Платформа (D0) не зависит **ни от одного** домена. Обратное — да.

## Что нужно подтвердить с бизнесом до G1

| Вопрос | Почему важно |
|---|---|
| Верна ли граница между D4 (договоры) и D5 (учёт)? | сейчас `ContractController` живёт в `marketing`, но работает со счетами и проводками — граница проведена по коду, а не по смыслу |
| D6 — отдельный домен или часть D5? | расчёт зарплаты — 7 598 строк в одном классе внутри `accounting`, при этом логически ближе к персоналу |
| Что такое `aes` и `newdev`? | 5 778 строк без понятного назначения — [OQ-004](../transition/12-open-questions.md) |
| Нужны ли D10 и D11 в новой системе? | 3 573 строки суммарно; возможно, дешевле готовое решение или отказ |
| Верно ли, что D8 и D9 — разные домены? | сейчас переплетены на фронтенде (`callcenter` и `crm/callCenter`) |

Ответы на эти вопросы меняют оценки. Пока они не получены, оценки Фазы 2 даны
диапазоном.
