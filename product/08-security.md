# Безопасность

Требования к безопасности системы. Модель доступа описана в
[ADR-0006](../docs/02-decisions/ADR-0006-auth-model.md); здесь — всё остальное.

Часть требований возникла из находок аудита действующей системы
([EPIC-010](../backlog/EPIC-010-security-audit.md)); сами находки здесь не
описываются — репозиторий публичный.

## Требования

### Транспорт

- TLS на всех внешних соединениях без исключений, включая внутренние контуры.
- HTTP-заголовки безопасности настраиваются на уровне платформы, а не отдельных
  эндпойнтов.
- Внутренние адреса и топология сети не раскрываются клиенту
  ([NC-11](../docs/01-principles/01-no-compromise.md#nc-11)).

### Аутентификация и сессии

- См. [ADR-0006](../docs/02-decisions/ADR-0006-auth-model.md).
- Токены короткоживущие, обновляемые, отзываемые.
- Выход из системы действительно завершает сессию на сервере.
- Одновременные сессии контролируемы; администратор может завершить сессию
  пользователя.

### Авторизация

- Каждый эндпойнт объявляет требуемое право ([NC-12](../docs/01-principles/01-no-compromise.md#nc-12));
  эндпойнт без объявленного права не проходит CI.
- Ограничение по области данных (филиал, компания, подразделение) применяется в
  слое доступа к данным, а не в контроллере, — забыть его должно быть
  невозможно.
- Отказ в доступе журналируется с причиной.
- Прямое обращение к объекту по идентификатору проверяется на право доступа
  всегда — «пользователь не знает идентификатор» не является защитой.

### Данные

- Секреты — только из хранилища секретов; в репозитории, образе, переменных
  сборки и журналах их нет. Проверяется автоматически.
- Персональные данные не попадают в журналы, сообщения об ошибках и метрики.
- Шифрование данных при хранении и при передаче.
- Доступ к промышленным данным — по заявке, с журналированием; копии для
  разработки и тестирования **обезличиваются** — это требование к инструменту
  подготовки данных, а не пожелание.
- Экспорт больших объёмов данных пользователем — журналируемое событие с
  ограничением частоты.

### Ввод и вывод

- Валидация всех входных данных на границе по схеме из спецификации API.
- Параметризованные запросы всегда; конкатенация SQL запрещена и проверяется
  автоматически ([NC-05](../docs/01-principles/01-no-compromise.md#nc-05)).
- Загружаемые файлы: ограничение типа и размера, проверка содержимого, хранение
  вне корня веб-сервера, выдача через контролируемый эндпойнт с проверкой прав.
- Ограничение частоты запросов на уровне пользователя и на уровне точки входа.

### Зависимости и сборка

- Сканирование уязвимостей зависимостей на каждом PR; критические находки
  блокируют слияние ([NC-09](../docs/01-principles/01-no-compromise.md#nc-09)).
- Фиксация версий (lock-файл), воспроизводимая сборка ([NC-08](../docs/01-principles/01-no-compromise.md#nc-08)).
- Базовые образы обновляются регулярно и автоматически пересобираются.
- Состав программного обеспечения (SBOM) формируется при сборке.
- Статический анализ безопасности в пайплайне.

### Эксплуатация

- Доступ к промышленному контуру — только через пайплайн
  ([NC-13](../docs/01-principles/01-no-compromise.md#nc-13)); интерактивный доступ к
  контейнерам приложения закрыт по умолчанию.
- Журнал административных действий неизменяем.
- Регулярное тестирование восстановления из резервной копии — учениями.
- План реагирования на инцидент безопасности с назначенными ролями.

## Требования регулятора

Требования к персональным данным, срокам хранения, локализации данных и
неизменяемости журналов операций не подтверждены и являются
[OQ-003](../transition/12-open-questions.md). Ответ на них может добавить
существенный объём работы (например, требование хранить данные в определённой
юрисдикции или обеспечить неизменяемость финансовых журналов) — до его
получения оценки Фазы 1 остаются диапазоном.
