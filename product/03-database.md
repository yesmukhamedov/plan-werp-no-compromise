# База данных

PostgreSQL ([ADR-0002](../docs/02-decisions/ADR-0002-database-postgresql.md)).
Документ состоит из двух частей: **правила**, по которым устроена любая таблица
системы, и **реестр** всех таблиц с их состоянием.

Полные спецификации колонок и индексов — в [spec/](spec/README.md), по файлу на
домен.

---

# Часть I. Правила

## Организация

- Одна база, **схема на домен**; имя схемы = код домена из
  [карты](02-domains.md) в нижнем регистре (`reference`, `contract`,
  `accounting`, …).
- Домен пишет и читает только свою схему.
- Внешние ключи — только внутри схемы. Между доменами — ссылка по
  идентификатору **без** ограничения целостности на уровне БД; целостность
  обеспечивает прикладной слой.
- Общие справочники живут в схеме `reference` и доступны другим доменам через
  её публичный интерфейс, а не прямым запросом.

## Именование

| Объект | Правило | Пример |
|---|---|---|
| Схема | `snake_case`, код домена | `accounting` |
| Таблица | `snake_case`, **единственное** число | `contract`, `posting` |
| Связующая таблица | `<a>_<b>` по алфавиту | `contract_product` |
| Столбец | `snake_case` | `created_at`, `total_amount` |
| Первичный ключ | **всегда** `id` | |
| Внешний ключ | `<сущность>_id` | `customer_id` |
| Логический флаг | `is_<признак>` / `has_<признак>` | `is_active` |
| Момент времени | `<действие>_at` | `approved_at` |
| Индекс | `ix_<таблица>__<столбцы>` | `ix_branch__company_id` |
| Уникальный индекс | `ux_<таблица>__<столбцы>` | `ux_country__code` |
| Ограничение-проверка | `ck_<таблица>__<смысл>` | `ck_contract__amount_positive` |
| Внешний ключ (ограничение) | `fk_<таблица>__<столбец>` | `fk_branch__company_id` |
| Последовательность | не используется явно — см. «Идентификаторы» | |

Три запрета, проверяемые автоматически:

1. **Транслитерация и чужие сокращения запрещены.** Имя столбца должно быть
   понятно человеку, впервые открывшему схему.
2. **Один смысл — одно имя во всей системе.** Идентификатор страны называется
   `country_id` везде, а не `country_id` в одной таблице и `countryid` в
   соседней.
3. **Имя не кодирует тип или длину.** Столбец с названием филиала называется
   `name`, а не `text45`.

## Обязательные столбцы

Каждая изменяемая сущность:

| Столбец | Тип | Назначение |
|---|---|---|
| `id` | см. «Идентификаторы» | первичный ключ |
| `created_at` | `timestamptz` | момент создания |
| `created_by` | `uuid` | автор создания |
| `updated_at` | `timestamptz` | момент последнего изменения |
| `updated_by` | `uuid` | автор последнего изменения |
| `version` | `integer` | оптимистическая блокировка |

**`version` обязателен, а не опционален.** Без него параллельное редактирование
одной записи двумя пользователями молча теряет одно из изменений.

Удаление — логическое (`deleted_at`, `deleted_by`) везде, где запись участвует
в истории или отчётности; физическое — только с обоснованием в описании
миграции.

Справочные таблицы, не меняющиеся в эксплуатации (коды валют, коды стран),
освобождаются от `version` — но не от `created_at` / `updated_at`.

## Идентификаторы

- Тип — `uuid` (версия 7 или иная монотонная), генерируется приложением.
- Монотонность обязательна: случайный UUID разрушает локальность вставки в
  индекс и на объёмах ERP это измеримо.
- Естественные ключи (код валюты, код страны) остаются отдельным столбцом с
  уникальным индексом, но **не становятся первичным ключом**: они меняются
  чаще, чем кажется, и их изменение каскадом ломает ссылки.

## Типы

| Что | Тип | Почему |
|---|---|---|
| Деньги | `numeric(19,4)` + столбец валюты | точность обязательна |
| Проценты, коэффициенты | `numeric(9,6)` | |
| Количество | `numeric(19,6)` | дробные количества существуют |
| Момент времени | `timestamptz`, хранение в UTC | часовой пояс не зашивается в образ |
| Дата | `date` | |
| Идентификатор | `uuid` | |
| Короткий текст | `text` + `ck`-ограничение на длину | `varchar(n)` меняется миграцией, ограничение — нет |
| Перечисление | `text` + `ck`-ограничение со списком | значения читаемы в БД и в выгрузках |
| Флаг | `boolean` | не `char(1)`, не `number(1)` |
| Полуструктурированные данные | `jsonb` | **только с обоснованием в описании миграции** |
| Двоичные данные | не в БД | файлы — в файловом хранилище, в БД ссылка |

Запрещено и проверяется автоматически по схеме:

- `real` / `double precision` для денег и количеств;
- `timestamp` без часового пояса;
- `jsonb` как способ не проектировать схему;
- столбцы вида `field1`, `field2`, `reserved`, `note2`.

### Перечисления

Значение перечисления — читаемая строка (`ACTIVE`, `CANCELLED`), а не число.
Числовые коды состояний нечитаемы в выгрузке, требуют справочника в голове и
порождают «магические» константы в коде.

## Правила денежной арифметики

Определяются **один раз** на уровне платформы и не переопределяются доменами:

- хранение — 4 знака после запятой; представление — по валюте;
- правило округления — единое для системы, фиксируется здесь после
  подтверждения бухгалтерией `?`;
- сумма всегда сопровождается валютой; сложение сумм в разных валютах — ошибка
  времени выполнения, а не молчаливое приведение;
- курсы валют — версионированный справочник с датой действия; любой расчёт
  указывает, на какую дату взят курс.

## Локализация в данных

Переводимые значения справочников **не хранятся отдельными колонками**
(`name`, `name_kz`, `name_en`): добавление языка не должно требовать миграции
схемы.

Схема:

```
reference.country          id, code, ...
reference.country_name     country_id, locale, name      ux(country_id, locale)
```

Тексты интерфейса и сообщения об ошибках в БД не хранятся вовсе — они в системе
сообщений ([ADR-0010](../docs/02-decisions/ADR-0010-i18n.md)).

## Индексы

- Индекс создаётся **под конкретный запрос**; в описании миграции указывается,
  какой именно.
- Обязательный минимум на таблицу: первичный ключ; уникальные индексы на
  естественные ключи; индекс на каждый внешний ключ, по которому идёт выборка;
  индекс на `deleted_at` при логическом удалении, если выборки его фильтруют.
- Составной индекс — в порядке селективности, самый селективный первым.
- Частичный индекс (`WHERE deleted_at IS NULL`) предпочтительнее полного там,
  где выборка всегда фильтрует.
- Индекс, не используемый ни одним запросом, удаляется: он стоит на каждой
  вставке.

## Миграции

- Только версионированные, только вперёд, только через инструмент миграций.
- Каждая миграция применяется на копии промышленных данных до слияния.
- Ломающие изменения — в четыре шага, каждый отдельным релизом:
  **добавить → заполнить → переключить → удалить**.
- Автогенерация схемы в рантайме отключена во **всех** контурах, включая
  разработческий.
- Эталонные (справочные) данные версионируются вместе со схемой.
- Описание миграции обязательно объясняет: зачем изменение, какой запрос
  обслуживает новый индекс, как откатить.

## Аудит

- Аудит — подсистема платформы, единая для всех доменов, а не механизм ORM,
  подключаемый по вкусу домена.
- **Что аудируется — решение владельца домена, зафиксированное явно** в
  спецификации домена. Аудит «всего» и аудит «ничего» одинаково бесполезны.
- Запись аудита неизменяема и содержит: субъекта, время, сущность, действие,
  прежнее и новое значения, идентификатор запроса.
- Хранится в отдельной схеме `audit`, а не рядом с данными домена.
- Срок хранения — [OQ-003](../transition/12-open-questions.md#oq-003).

## Производительность

- Запросы профилируются на объёме, сопоставимом с промышленным.
- Проблема N+1 отлавливается тестом ([09-quality.md](09-quality.md)).
- Тяжёлое чтение (отчёты) — с реплики.
- Секционирование крупных исторических таблиц — по факту измеренного объёма, не
  заранее.

## Порядок проектирования

По графу зависимостей доменов ([02-domains.md](02-domains.md#граф-зависимостей)):
`platform` и `audit` → `reference` → `party` → `hr`, `contract` → `accounting` →
`payroll`, `logistics`, `legal` → `service`, `crm`. Схема не проектируется
раньше той, на которую ссылается.
