# Стратегия переезда

Реализация [ADR-0001](../docs/02-decisions/ADR-0001-strategy-big-bang.md). Переезд —
единственный момент, когда пользователи переходят со старой системы на новую.
Второй попытки в тот же день не будет, поэтому весь документ — про то, как
сделать этот момент скучным.

**Главный принцип: к боевому переезду это должна быть отрепетированная
процедура, а не событие.**

## Условия допуска к переезду

Переезд не начинается, пока не выполнено **всё** перечисленное. Список
проверяется формально, галочка ставится ответственным поимённо.

- [ ] DoD всех доменов выполнен ([01-principles/02-definition-of-done.md](../docs/01-principles/02-definition-of-done.md#dod-домена)).
- [ ] Теневой прогон идёт не менее 30 дней подряд; расхождения либо отсутствуют,
      либо приняты письменно ([03-parity-verification.md](06-parity-verification.md)).
- [ ] Расхождение финансовых расчётов — ноль.
- [ ] Проведено не менее **четырёх** полных репетиций миграции данных,
      последние **две подряд** — успешные.
- [ ] Время миграции укладывается в согласованное окно с запасом не менее ×2.
- [ ] План отката отрепетирован, время отката измерено и укладывается в норматив
      ([04-rollback.md](08-rollback.md)).
- [ ] Нагрузочные испытания на предпродуктивном контуре пройдены при ×3 от пика.
- [ ] Пользователи прошли обучение; приёмка подписана владельцами доменов.
- [ ] Ранбуки написаны, дежурная смена сформирована и знает их.
- [ ] Мониторинг и оповещения настроены и проверены на предпродуктивном контуре.
- [ ] Внешние контрагенты уведомлены об окне недоступности.
- [ ] Заморозка легаси действует, delta backlog пуст ([05-freeze-policy.md](09-freeze-policy.md)).
- [ ] Дата и время вывода легаси из эксплуатации назначены ([NC-07](../docs/01-principles/01-no-compromise.md#nc-07)).

Невыполнение любого пункта — перенос переезда. Это правило существует именно для
того, чтобы его применили под давлением сроков.

## Выбор окна

- Период минимальной деловой активности: не закрытие месяца, не начисление
  зарплаты, не пик сезонности. Конкретное окно выбирается по профилю нагрузки
  из [EPIC-009](../backlog/EPIC-009-baseline-measurement.md).
- Окно должно вмещать: миграцию + проверку + запас + **полный откат**. Если
  откат не помещается в окно, окно выбрано неверно.
- Рабочий день после переезда — с усиленной дежурной сменой и присутствием
  разработчиков доменов.

## Ход переезда

| Шаг | Действие | Обратимо |
|---|---|---|
| T−14д | Заморозка кода нового WERP; только исправления дефектов | да |
| T−7д | Финальная репетиция на свежей копии данных | да |
| T−2д | Уведомление пользователей и контрагентов | да |
| T−1д | Проверка резервных копий; подтверждение готовности по чек-листу | да |
| T−0 | **Начало окна.** Легаси переводится в режим только чтения | да |
| T+ | Финальная резервная копия легаси | да |
| T+ | Перенос данных | да |
| T+ | Автоматическая сверка перенесённых данных | да |
| T+ | Дымовые тесты на новой системе с промышленными данными | да |
| T+ | Ручная приёмка ключевых сценариев владельцами доменов | да |
| T+ | **Точка принятия решения:** идём дальше или откатываемся | ← последняя точка дешёвого отката |
| T+ | Переключение маршрутизации на новую систему | дорого |
| T+ | Легаси останавливается (не удаляется) | |
| T+ | Проверка внешних интеграций через `bridge` | |
| T+ | Открытие доступа пользователям | |
| T+1ч | Контроль показателей; решение о завершении окна | |

**Точка принятия решения — ключевой элемент процедуры.** До неё откат стоит
дёшево (легаси не менялся, данные не расходились). После неё в новой системе
появляются данные, которых нет в легаси, и откат становится дорогим
([04-rollback.md](08-rollback.md)). Критерии прохождения точки определяются
заранее и не смягчаются в ночь переезда.

## Стабилизация

- Легаси-контур сохраняется **работоспособным, но остановленным** на весь срок
  стабилизации (предварительно 30 дней, [OQ-011](12-open-questions.md)).
- Усиленное дежурство первые две недели.
- Ежедневная сверка ключевых показателей со значениями до переезда.
- Дефекты, обнаруженные пользователями, классифицируются по влиянию;
  блокирующие исправляются в тот же день.
- Порог, при котором принимается решение об откате в период стабилизации,
  определяется **до** переезда, а не по ситуации.

## После стабилизации

Начинается [Фаза 5](plan/06-phase-5-decommission.md): легаси
выводится из эксплуатации, Oracle и MySQL останавливаются, лицензии не
продлеваются, репозитории архивируются. Проект не считается завершённым, пока
это не сделано ([NC-07](../docs/01-principles/01-no-compromise.md#nc-07)).

## Роли на время переезда

| Роль | Ответственность |
|---|---|
| Руководитель переезда | единственный, кто принимает решение «идём» / «откат» |
| Ответственный за данные | миграция и сверка |
| Ответственный за инфраструктуру | маршрутизация, контуры, резервные копии |
| Владельцы доменов | ручная приёмка своих сценариев |
| Дежурная смена | наблюдение, реагирование |
| Связь с бизнесом | уведомления пользователям и контрагентам |

Роли назначаются поимённо не позднее T−14д. Решение об откате принимает один
человек — коллективное решение в три часа ночи не принимается.
