# Соответствие базы данных

Как существующая схема превращается в целевую
([product/03-database.md](../product/03-database.md)). Правила преобразования —
здесь, полные карты по доменам — в [map/](map/README.md).

Этот документ — источник требований для инструмента миграции
([EPIC-005](../backlog/EPIC-005-data-migration.md)) и для проектирования целевой
схемы ([EPIC-003](../backlog/EPIC-003-schema-inventory.md)).

# Часть I. Что придётся преобразовать

Разбор унаследованной схемы на примерах, которые определяют объём работы. Все
примеры взяты из действующего кода.

## 1. Имена, унаследованные от чужой ERP

Значительная часть схемы называется терминами системы, из которой WERP когда-то
вырос: `bukrs`, `matnr`, `lifnr`, `werks`, `spras`, `hkont`, `blart`, `bschl`,
`shkzg`, `meins`. Понять схему, не зная этой номенклатуры, невозможно.

Отдельный случай — **имя, кодирующее тип, а не смысл**: колонка `text45`
содержит наименование филиала. Таких колонок в схеме несколько.

**Правило:** каждое унаследованное сокращение расшифровывается один раз
([TASK-0309](../backlog/EPIC-003-schema-inventory.md)) и заменяется осмысленным
именем. Таблица соответствий имён — часть [GLOSSARY.md](../GLOSSARY.md) и часть
инструмента миграции.

## 2. Три разных способа назвать одно и то же

В унаследованной схеме идентификаторы именуются как минимум тремя способами
одновременно:

| Пример | Таблица | Форма |
|---|---|---|
| `branch_id` | `branch` | `<сущность>_id` |
| `country_id` | `branch` | `<сущность>_id` |
| `countryid` | `city` | без разделителя |
| `stateid` | `city` | без разделителя |
| `idcity` | `city` | префикс `id` |

Три формы встречаются **в соседних таблицах, ссылающихся друг на друга**.

**Правило:** первичный ключ всегда `id`, внешний — `<сущность>_id`
([product/03-database.md](../product/03-database.md#именование)).

Регистр имён также не единообразен: `TOVAR_CATEGORY` в верхнем регистре рядом с
`business_area_id` в нижнем, в одной таблице.

## 3. Две сущности на одну таблицу

Классы `Company` и `Bukrs` — оба `@Table(name = "company")`, с одинаковым
набором полей (`bukrs`, `spras`, `name`). Две модели одной таблицы, живущие
параллельно.

**Правило:** одна таблица — одна модель. При сведении выбирается модель,
используемая большим числом сценариев; вторая удаляется вместе с зависимым
кодом ([02-backend-mapping.md](02-backend-mapping.md)).

## 4. Класс и таблица называются по-разному

Класс `Werks` отображается на таблицу `werks_type`. Класс `Bukrs` — на
`company`. Связь между именем в коде и именем в БД не выводится.

**Правило:** имя модели соответствует имени таблицы в единственном числе.

## 5. Идентификаторы промышленных данных в коде

В сущности `Branch` объявлены константы вида
`GREEN_LIGHT_MAIN_BRANCH_ID = 207L` и `AURA_MAIN_BRANCH_ID = 2L` — конкретные
значения первичных ключей промышленной базы, зашитые в код.

Это делает код зависимым от содержимого базы: те же исходники на другом наборе
данных ведут себя иначе, а тестовые данные обязаны воспроизводить конкретные
идентификаторы.

**Правило:** поведение, зависящее от конкретной записи, выражается **признаком
в данных**, а не идентификатором в коде. Для примера выше — колонка
`branch.kind = HEAD` и `warehouse.is_main`, а не сравнение с числом.

Выявление всех таких констант — обязательная задача
[EPIC-003](../backlog/EPIC-003-schema-inventory.md): каждая требует
проектного решения, какой признак её заменяет.

## 6. Служебные столбцы применены выборочно

Замеры по унаследованному коду:

| Признак | Найдено | Из 523 сущностей |
|---|---:|---|
| Столбец `created_at` (в любом написании) | 66 | ~13 % |
| Столбец `updated_at` | 34 | ~7 % |
| Столбец `created_by` | 97 | ~19 % |
| Оптимистическая блокировка (`@Version`) | **6** | ~1 % |
| Аудит изменений (`@Audited`) | **7** | ~1,3 % |

Базовый класс сущностей (`AbstractEntity`) **не содержит ни одного поля** — он
пустой, поэтому единого набора служебных столбцов в схеме нет.

**Следствия для перехода:**

- у большинства таблиц **нет истории**: кто и когда создал запись,
  восстановить невозможно. При миграции такие столбцы заполняются пометкой
  «мигрировано», а не выдуманными значениями;
- аудит изменений существует для 7 сущностей — их история переносится
  ([C-10](../docs/00-context/03-constraints.md#c-10-аудит-изменений-уже-существует-и-должен-сохраниться)),
  для остальных история начинается с момента переезда, и это нужно сообщить
  пользователям заранее;
- оптимистической блокировки практически нет — значит, параллельные правки
  сейчас теряются молча. В продукте `version` обязателен, и это **изменение
  поведения**, которое пользователи заметят: они начнут получать сообщение о
  конфликте вместо потери данных.

## 7. Локализация колонками

Переводы хранятся отдельными колонками (`name`, `name_kz` в таблице `city`)
параллельно с системой сообщений в файлах. Добавление языка требует миграции
схемы.

**Правило:** парные таблицы наименований
([product/03-database.md](../product/03-database.md#локализация-в-данных)). При
миграции колонки разворачиваются в строки.

## 8. Денормализация без синхронизации

Таблица `country` содержит одновременно `currency_id` (ссылку) и `currency`
(строку). Согласованность ничем не обеспечена.

**Правило:** одно значение хранится в одном месте. При миграции выбирается
источник истины, расхождения фиксируются в журнале отбраковки и разбираются
владельцем домена.

## 9. Числа вместо перечислений

Тип филиала хранится числом (`type`), а его значения определены константами в
коде (`TYPE_MAIN = 1`, `TYPE_REGION = 2`, `TYPE_BRANCH = 3`, `TYPE_CITY = 4`).
В выгрузке из БД видно `2`, и что это значит — знает только код.

Аналогично `is_main` объявлен как `int`, а не логический тип.

**Правило:** перечисления — читаемые строки, флаги — `boolean`
([product/03-database.md](../product/03-database.md#типы)). Соответствие
«число → строка» задаётся в карте домена.

# Часть II. Правила преобразования

Применяются к каждой колонке. Инструмент миграции реализует их
([TASK-0501](../backlog/EPIC-005-data-migration.md)).

| Что | Правило | Проверка |
|---|---|---|
| Имя таблицы | единственное число, `snake_case`, без сокращений | ревью + линтер схемы |
| Имя колонки | `snake_case`, без транслитерации, без кодировки типа | то же |
| Первичный ключ | новый `uuid`; старое значение сохраняется в таблице соответствия | сверка по количеству |
| Внешний ключ | переадресуется через таблицу соответствия | ссылочная сверка |
| Пустая строка | Oracle не отличает от `NULL` — по каждому столбцу явное решение | выборочная сверка |
| Дата и время | → UTC с явным указанием исходной зоны | сверка на граничных значениях |
| Деньги | `numeric(19,4)`, округление по правилу платформы | **сверка до копейки** |
| Логическое | `int` / `char(1)` → `boolean` с явным списком допустимых входных значений | сверка количеств по значениям |
| Перечисление | число → строковый код по таблице соответствия домена | сверка количеств по значениям |
| Локализованное имя | колонки `name`, `name_kz` → строки в `*_name` | сверка количеств |
| Служебные столбцы | отсутствующие заполняются пометкой миграции | — |
| Мёртвые столбцы | не переносятся | зафиксировано решение |

## Сохранение старых идентификаторов

Целевая схема использует `uuid`, унаследованная — числа и строки. На время
проекта ведётся таблица соответствия:

```
migration.id_map(source_schema, source_table, source_id, target_id)
```

Она нужна для: переадресации внешних ключей; сверки «строка к строке»;
разбора расхождений в теневом прогоне; ручного переноса данных при откате О2
([08-rollback.md](08-rollback.md#о2-поздний-откат)).

Таблица удаляется в [Фазе 5](plan/06-phase-5-decommission.md) вместе с легаси.

преобразования. Разнесённые во времени, они расходятся.
