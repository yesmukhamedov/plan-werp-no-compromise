# D1. Справочники — карта соответствий

Парная к [product/spec/D1-reference.md](../../product/spec/D1-reference.md).
Образец обязательной глубины для остальных доменов.

Все сведения об источнике получены из действующего кода. Ячейки «не
подтверждено» означают, что данные требуют проверки в
[EPIC-003](../../backlog/EPIC-003-schema-inventory.md), а не что их не искали.

## Решения по сведению

Домен собирается из двух параллельных реализаций — главный источник работы.

| Вопрос | Решение | Обоснование | Кто принял |
|---|---|---|---|
| `reference` или `mreference` — источник истины? | **разделяем по смыслу**, а не выбираем одну | `mreference` содержит клиентов, адреса и телефоны — это не справочники, а контрагенты | не принято |
| Куда уходят `Address`, `Customer`, `Phone`, `PhoneChannel` из `mreference` | → домен **D2 Контрагенты** | у контрагента есть жизненный цикл, у справочника нет | не принято |
| Куда уходит `BusinessArea` (есть в обеих) | → D1, одна реализация | дубль | не принято |
| `Company` и `Bukrs` — две модели таблицы `company` | одна модель `Company` | одинаковый набор полей | не принято |
| Механизм `*F4` (34 класса) | **упраздняется** | заменяется списочными эндпойнтами с поиском | не принято |
| 15+ мелких справочников | → `reference_list` / `reference_item` | 3–5 колонок каждый; отдельные таблицы = 15-кратное дублирование кода | не принято |

> Строка «разделяем по смыслу» — пример того, как решение о сведении меняет
> границы **двух** доменов сразу. Такие решения принимает владелец, а не
> разработчик.

### Константы промышленных данных в коде

В классе `Branch` объявлены `GREEN_LIGHT_MAIN_BRANCH_ID = 207L` и
`AURA_MAIN_BRANCH_ID = 2L` — идентификаторы конкретных записей промышленной
базы, зашитые в исходники
([01-database-mapping.md](../01-database-mapping.md#5-идентификаторы-промышленных-данных-в-коде)).

| Константа | Что означает | Чем заменяется | Действие |
|---|---|---|---|
| `AURA_MAIN_BRANCH_ID` | головной филиал основной компании | `branch.kind = HEAD` + `company_id` | найти все использования |
| `GREEN_LIGHT_MAIN_BRANCH_ID` | головной филиал второй компании | то же | то же |

Найти **все** места, где эти константы используются, — обязательная задача
разбора домена: каждое место содержит бизнес-правило, выраженное через
идентификатор записи.

**Проверки, которые нужно выполнить обязательно:**

- связность дерева филиалов: нет циклов, нет висящих `parent_branch_id`, у
  каждой компании ровно один корень;
- согласованность `country.currency_id` и `country.currency`;
- заполненность `name_kz` в `city` — от неё зависит полнота локализации;
- ссылочная целостность `city.stateid` → `state`, `state → country`;
- дубликаты в справочниках, схлопываемых в `reference_item`.

### Разбор `ReferenceRestController`

Ключевая задача домена и одна из первых в проекте
([02-backend-mapping.md](../02-backend-mapping.md#приоритеты-разбора)). Из 72
эндпойнтов класса в D1 остаётся меньшая часть.

| `/companies`, `/countries`, `/states`, `/cities`, `/regions`, `/branches/*`, `/products`, `/product-categories`, `/oper-types`, `/spare-part-*` | **D1** |
| `/crm/staffListForCrm`, `/crm/staffListAllForCrm`, `/positions` | D3 Персонал |
| `/crm/salaryListForCrm/{staffId}`, `/crm/salaryListByYearAndMonthForCrm` | D6 Расчёт вознаграждений |
| `/crm/dealersContractSales*` | D4 Договоры и продажи |

| `/reasons/{type}` | D1, → `reference_item` |

Этот разбор — не только про API: он показывает, где проходят **реальные**
границы доменов, и потому выполняется до подтверждения карты доменов

### `fetchCountries` возвращает сущность

`GET /FETCH_COUNTRIES` отдаёт `Map<Long, Country>` — JPA-сущность напрямую, без
DTO. Клиент получает структуру таблицы.

При переносе форма ответа меняется на описанную в спецификации. **Это ломающее
изменение** для всех, кто им пользуется, — список потребителей нужно установить
до переноса (TASK-0203).

## Изменения поведения

Что пользователь заметит после переезда. Каждый пункт требует решения владельца
домена **до** реализации.

| Изменение | Что увидит пользователь | Решение |
|---|---|---|
| Удаление филиала → деактивация | кнопка «Удалить» становится «Деактивировать»; записи не исчезают | не принято |
| Появление `version` | сообщение «запись изменена другим пользователем» вместо молчаливой потери правок | не принято |
| Мелкие справочники на одном экране | пять пунктов меню становятся одним | не принято |
| Модальные окна выбора → компонент | единообразное поведение вместо разного в разных окнах | не принято |
| Пагинация в списках | города и номенклатура больше не грузятся целиком | не принято |
| Новое поле `code` у филиала | обязательное поле, которого не было | **требует заполнения данных до переезда** |
| Дерево филиалов вместо плоского списка | новый способ навигации | не принято |
| Отдельный справочник валют | валюта перестаёт быть строкой в стране | не принято |

Предпоследняя строка — пример находки, которая **должна попасть в план очистки
данных**: если у филиалов нет кода, его нужно проставить в легаси до переезда, а
не выдумывать при миграции
([05-data-migration.md](../05-data-migration.md#э4-качество-данных)).

## Риски домена

| # | Риск | Проявление | Действие |
|---|---|---|---|
| D1-R1 | У филиала нет колонки `code` | новое обязательное поле нечем заполнить | решить: генерировать, заполнить вручную в легаси или отказаться от обязательности |
| D1-R2 | Связность дерева филиалов не проверена | циклы или висящие ссылки в промышленных данных | проверить в TASK-0304, до проектирования `path` |
| D1-R3 | `city_id` у филиала восстанавливается косвенно | часть филиалов останется без города | измерить долю; при значительной — заполнять вручную |
| D1-R4 | Константы промышленных ID в коде | пропущенное использование ломает бизнес-правило | найти все использования, каждое — отдельное решение |
| D1-R5 | Потребители `FETCH_COUNTRIES` неизвестны | ломающее изменение формы ответа | установить список потребителей до переноса |
| D1-R6 | `mreference` содержит не только справочники | граница D1/D2 проведена неверно | подтвердить разделение с владельцами обоих доменов |
| D1-R7 | Разбор `ReferenceRestController` меняет карту доменов | 13 эндпойнтов уезжают в четыре других домена | выполнить разбор **до** подтверждения карты доменов на G1 |

D1-R7 — причина, по которой этот домен разбирается первым: его разбор влияет на
границы других доменов, а не только на него самого.
