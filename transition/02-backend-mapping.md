# Соответствие бэкенда

Какой существующий класс чем заменяется в целевой структуре
([product/04-backend.md](../product/04-backend.md)).

---

# Часть I. Почему это не перенос «класс в класс»

Соответствие здесь **не однозначное**, и это главное, что нужно понимать при
планировании.

## Один класс → много классов

`ContractController` — 3 775 строк, 38 полевых инъекций. Он содержит:
транспорт, бизнес-логику, обращения к семи чужим доменам, формирование отчётов,
отправку SMS.

В целевой структуре он превращается примерно в: 1 контроллер (≤ 200 строк),
6–10 обработчиков сценариев, 2–4 доменных сервиса, несколько правил, вызовы
фасадов чужих доменов вместо прямых обращений к их DAO.

Аналогично `PayrollService` (7 598 строк), `FinanceServiceDms` (5 629),
`FinanceReportRestController` (5 366), `ServiceTableService` (3 984),
`InvoiceServiceImpl` (2 375).

**Следствие для оценки:** трудоёмкость домена не пропорциональна числу
унаследованных классов. Один god-класс дороже двадцати мелких.

## Много классов → один

Дублирующиеся домены схлопываются: две реализации CRM (модуль `crm` и
репозиторий `werp_crm`), две реализации справочников (`reference` и
`mreference`), две реализации сервисного обслуживания.

**Следствие:** перед переносом нужно решить, какая реализация правильная. Это
не техническое решение — его принимает владелец домена
([OQ-002](12-open-questions.md#oq-002)).

## Класс → ничего

Исчезают целые категории:

| Что исчезает | Сколько | Чем заменяется |
|---|---|---|
| Классы `*F4` — «помощь по значению» | 34 в одном домене | обычные списочные эндпойнты с поиском |
| Слой `dao/` с `DAOException` | по домену | репозитории |
| Ручные обёртки над HTTP, DTO | сотни | генерация из спецификации |
| `util`, `main-module` как свалка общего | 293 файла | платформенные модули с явными границами |
| Классы, обслуживающие мёртвые эндпойнты | неизвестно | ничего |

## Ничего → класс

Появляется то, чего в унаследованной системе нет вовсе: фасады доменов,
доменные события и подписчики, правила как отдельные классы, обработчики
сценариев, тесты, платформенные модули (12 штук), слой совместимости для
мобильного приложения.

**Это существенная часть работы, у которой нет предшественника** — и её
регулярно забывают при оценке «переписывания».

# Часть II. Правила соответствия

## По типам классов

| Было | Стало | Правило |
|---|---|---|
| `*Controller` с логикой | `*Controller` + `*Handler` | контроллер оставляет только транспорт |
| `*Service` (god-класс) | несколько `*Handler` + `*Service` + `*Rule` | разделение по сценариям |
| `*ServiceImpl` + интерфейс | один класс | интерфейс с единственной реализацией не создаётся |
| `*Dao`, `*DaoImpl` | `*Repository` | один механизм доступа к данным |
| `@Entity` (таблица) | сущность домена + `*Record` | доменная модель отделяется от строки таблицы |
| `*F4` | эндпойнт списка с поиском | отдельного механизма подсказок нет |
| DTO ручные | генерируются из спецификации | |
| `*Util`, `*Helper` | доменное правило или платформенный модуль | классов с такими именами не существует |
| прямая инъекция чужого DAO | вызов фасада чужого домена | [NC-02](../docs/01-principles/01-no-compromise.md#nc-02) |

## Правило «поведение, а не код»

Существующая реализация — **источник требований**, а не образец. Читаем, чтобы
понять, что система делает; пишем заново, зная зачем.

Признак нарушения: в целевом классе появляется структура, объяснимая только
историей унаследованного кода.

## Что переносится дословно

Одна категория переносится максимально близко к оригиналу — **формулы расчётов**
(денежные, зарплатные, налоговые). Их поведение зафиксировано
характеризационными тестами ([EPIC-004](../backlog/EPIC-004-characterization-tests.md))
и должно совпадать до копейки.

Переносится **формула**, а не её оформление: расчёт из метода на 400 строк
становится набором правил с теми же результатами на тех же входных данных.

## Приоритеты разбора

Классы, требующие проектного решения раньше остальных, — по убыванию влияния:

| Класс | Строк / инъекций | Почему первым |
|---|---|---|
| `PayrollService` | 7 598 | деньги людей; частные случаи за 12 лет |
| `ReferenceRestController` | 1 934 / 51 | содержит эндпойнты CRM, HR и продаж внутри домена справочников — разбор задаёт границы сразу нескольких доменов |
| `FinanceServiceDms` | 5 629 / 21 | учёт |
| `FinanceReportRestController` | 5 366 / 20 | отчёты, недооценённая часть |
| `ContractController` | 3 775 / 38 | семь чужих доменов в одном классе |
| `ServiceTableService` | 3 984 / 48 | наибольшее число зависимостей |
| `util` + `main-module` | 293 файла | пока не разобраны, платформа не спроектирована |

`ReferenceRestController` разбирается **первым среди контроллеров**: он
обслуживает эталонный домен D1 и одновременно показывает, где проходят реальные
границы между доменами.

Полная карта классов домена — [map/](map/README.md), образец —
[map/D1-reference.md](map/D1-reference.md#классы).
